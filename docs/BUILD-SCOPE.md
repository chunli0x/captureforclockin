# Production hardening, store distribution, durable backend, video, and mainnet payout scope

**Planning baseline: 2026-10-27. This is an engineering scope, not an implementation or deployment record.** Only this document was written. No application changes, builds, tests, migrations, chain transactions, publication, or deployment were performed for this scope. Historical test counts in other documents are not current verification.

**Priority:** establish secure, recoverable operation first; move settlement off HTTP requests; prove capacity and recovery; enable bounded mainnet $SKR payouts; distribute through stores; add video later. Proposed v1 is an image-judgment release with a durable backend and bounded mainnet $SKR payouts. USDC receives equivalent hardening and durability independently; its mainnet activation is a separate decision.

**Confidentiality applies to every workstream.** Public descriptions use only “robot vision” or “vision-model output preference.” Public artifacts, examples, screenshots, rubrics, filenames, URLs, crash reports, transaction memos, support materials, and served media must not disclose the underlying application. Do not copy internal research documents into public repositories or publication metadata. Neutral wording must remain truthful about data use, camera processing, financial terms, and privacy. Treat all material distributed to reviewers as potentially public. Automated text/metadata checks supplement human visual review; neither naming nor access control makes revealing imagery safe.

**Dual-build invariant:** SKR and USDC retain separate Android identities, program identities, backend processes, databases, migration histories, service credentials, treasuries, worker queues, caches, asset access policies, and release manifests. A shared engineering pattern does not authorize sharing financial state or converting balances. Each network adds another isolation boundary: devnet records never become mainnet liabilities by renaming columns.

1. **Do not redo signing scaffolding:** Clock In and USDC already have it; secure key custody, release CI, R8, certificate verification, and actual device/store validation remain. `tap-ci/android/app/build.gradle.kts` lacks the stronger release validation/signing configuration, so runtime-tree reconciliation is necessary.

USDC `Anchor.toml` also retains the SKR localnet ID despite its distinct compiled/devnet identity.
3. **Health is not a production certificate:** `/health` reports `production_ready` from DB/schema/chain checks and payout readiness from key availability; it does not prove treasury funding, security, workers, or DR. Historical deployment claims in `docs/judgment-api-contract.md` are not live proof. That document also contradicts actual storage names, no-work responses, and payout implementation.
4. **Calibration is not currently a gate.** `/judge/next` returns judgment work after liveness/bond checks; deposit and submission do not require calibration. The retained calibration endpoint branch/tables do not provide an active quality barrier. `over_18` is stored as a declaration, not enforced by the financial/judgment routes.

## 3. Durable backend workstream — primary engineering investment

**Owner:** backend/SRE lead; chain engineer owns external-effect correctness. Budget roughly half the implementation effort here. The target is bounded resource use, durable accepted work, recovery without user retries, and a measured path to higher throughput. Replica count alone does not solve shared database, signer, RPC or chain-account bottlenecks.

### 3.1 Deployment and scaling model

Proposed topology, instantiated separately for SKR and USDC:

```text
Android -> protected API hostname -> edge proxy/WAF -> Caddy/load balancer
                                                   -> API replicas (no signing keys)
                                                       -> PgBouncer -> product Postgres
                                                       -> product Redis (quotas/cache)
Product Postgres outbox -> product workers/reconciler -> restricted signer -> RPC A/B
Approved media -> product object bucket -> authenticated CDN delivery (video phase)
Telemetry -> restricted collectors; backups -> separate off-host storage
```

1. **First make one instance recoverable:** inventory actual service files; add reproducible manifests under proposed `capture-infra/services/{skr,usdc}/`, pinned image digests, resource quotas, non-root users, graceful shutdown, restart policy and private ports. Preserve `capture-seeker`/`capture-seeker-usdc` routing while creating explicit worker services (`capture-seeker-worker`, `capture-seeker-usdc-worker`). Use separate service users and secrets. No database or Redis exposed to the Internet.
2. **Remove process state/startup DDL before adding workers or API replicas.** Put liveness in Postgres (section 3.4); all HTTP instances share the appropriate database, not sticky sessions. Keep a bounded synchronous SQLAlchemy stack initially; extracting chain work is more valuable than converting every handler to `async def` while retaining blocking calls.
3. **Availability stage:** at least two API instances across two hosts; an edge/LB capable of routing around a lost origin, not merely two replicas behind the original single Caddy/VPS. Isolate each product's worker and Redis service. Move Postgres off the app host, with an HA option per product or explicit manual-failover RTO; separate DBs/roles are the minimum, separate clusters improve fault isolation. Maintain SKR/USDC CPU, DB, Redis and RPC quotas even if hardware is shared temporarily. An independent host failure must not take both replicas down.
4. **Scaling stage:** API replica count follows p95 latency/in-flight requests/CPU, bounded by total DB connections. Worker count follows ready-job age and RPC/signing budgets. Limit concurrent writes to shared treasury/fee-payer/bond accounts to avoid chain lock contention; more workers can otherwise reduce throughput. Sharded funded treasury lanes are a later measured optimization, not a prerequisite to an unbounded launch.
5. **Traffic ramp:** invitation cohorts → capped paid pilot → larger cohorts only after soak/load/DR gates. Preserve independent rollback and maintenance switches for each product. Pause new paid assignments when backlog, treasury coverage or RPC health crosses thresholds while keeping status/recovery available.

Proposed initial sizing for benchmarking, **not an established capacity claim**: each product gets two API processes (one per host), two worker processes with concurrency 2, its own Redis instance, and a Postgres capacity allocation starting around 4 vCPU/16 GiB RAM with SSD. Confirm host availability, IO budget and current dataset sizes before procurement. Avoid increasing workers until RPC/chain measurements support it.

### 3.2 Capacity contract and load model

Agree targets in week 1. Starting test envelope **per product**: 500 concurrent sessions; 100 authenticated read requests/second; 10 accepted judgments/second for a 30-minute burst; a four-hour realistic soak; a 10× rejected-abuse burst. This is an API/admission target, not a promise that a single treasury can finalize that payment throughput. Run both products concurrently to reveal shared-host contention.

* HTTP target: p95 reads <300 ms, accepted submissions <500 ms after admission; unexpected 5xx <0.5%. Intentionally shed 429/503 responses are reported separately, never hidden to improve the error metric.
* Normal-load worker target: reservation/payout p95 <120 seconds and oldest ready financial job <5 minutes when the network/provider is healthy. Measure finality delays separately. Reduce admission if the worker service rate does not meet this envelope.
* Initial availability objective: 99.9% monthly API availability, supported by multi-host ingress/app and tested DB failover; it is not a claim for the current VPS.
* Capacity math: measured judgment rate `J`, mean paid fraction `f`, and average chain operations per accepted judgment `c` imply approximately `J*c` transactions/second and `J*f` payouts/second, plus anchors/bond traffic. Reservation + release + payment often means 2–3 chain transactions per vote. Polling multiplies RPC traffic; batching confirmations is necessary.
* Queue backlog `B` drains in `B / (service_rate - arrival_rate)` seconds only if service exceeds arrivals. Gate burst admission by maximum outstanding jobs **and payout liability**, not a Redis count alone. Stress a 30-minute RPC outage at the admitted rate and prove the configured maximum bounds storage/cost.
* Storage estimate: daily votes × retained row/journal/index bytes × retention period, plus WAL, backups and free headroom. At 10/s continuously, 864,000 rows/day is a sizing scenario, not a usage forecast; measure actual row/index sizes on a synthetic million-vote dataset before choosing retention/partitions.

### 3.4 Postgres design, migrations and transaction discipline

**New durable records:** migration ledger (`version/checksum/applied_at/build_family`), deployment identity (`family/network genesis/program/mint/decimals/schema`), liveness sessions, work assignments, jobs/outbox, chain attempts, immutable reward obligations, budget reservations, per-wallet risk decisions, audit events. Keep existing judgment journals readable during migration; introduce an explicit versioned money ledger rather than silently repurposing the existing token-named columns. Signed transaction bytes require restricted access, encrypted storage/backups and log exclusion.

**Pool budget:** example per product: two API processes × pool 5/max overflow 0 = 10, two workers × pool 3 = 6, reconciliation/admin reserve 4 = 20 backend connections initially. Allocate a PgBouncer server-pool cap (e.g. 30 including headroom) and keep Postgres `max_connections` above aggregate allocations plus replication/operations reserves. If products temporarily share a Postgres instance, add both allocations. Multiplying Uvicorn workers multiplies pools. Verify psycopg prepared-statement behavior with the chosen transaction-pooling mode. Set explicit pool-wait (~1 s), API statement (~2 s), lock (~500 ms), and idle-in-transaction (~5 s) starting limits; tune for measured workloads. Jobs use separate, bounded statement limits; no network inside a DB transaction.

**Indexes to validate with `EXPLAIN (ANALYZE, BUFFERS)` on representative data:**

* `judgment_pairs(status, created_at, pair_id)` partial to open/collecting/rerouted work; randomized candidate selection avoids concentrating every wallet on the oldest pair.
* `judgments(wallet, submitted_at DESC)` partial where `aligned IS NOT NULL`; a neutral-payment window index with wallet/time and choice/earned predicate.
* Partial pending-work indexes for settlement/enforcement/unreserved liability states; `jobs(status, next_attempt_at, priority, id)` and `lease_until`; unique logical job keys.
* `assignments(wallet,status,expires_at)` and pair capacity indexes; unique active wallet/pair assignment.
* Expiry indexes for auth/liveness/limiter cleanup and `Prepared(wallet,action,target,last_valid_height DESC)` for operation reuse.
* Preserve unique pair/wallet judgment and unique prepared signature constraints; add checks for nonnegative monetary amounts and legal status transitions where practical.

Replace lifetime aggregation in `/judge/stats` with transactionally maintained earned/settled totals or a ledger projection with reconciliation; keep pending separate. Cache projections only for display. Paginate `/transactions` with a cursor beyond its current last-100 limit and bound dataset exports. Do not partition solely on forecast: benchmark first; use time partitioning for high-volume attempts/audit events when retention/vacuum warrants it, preserving uniqueness semantics for financial IDs.

**Migrations:** one migrator per product under an advisory lock using a DDL role; runtime role has only required DML. Establish a verified baseline for existing 0011–0015, then checksummed forward migrations with preconditions. Lock deployment identity before touching legacy renames; reject the opposite build even when schema looks similar. If both old/new columns exist, compare and stop on disagreement. Expand → backfill in chunks → deploy compatible readers/writers → validate → contract in a later release. Create large indexes concurrently outside transaction-wrapped migration steps where required; impose DDL lock timeout. Test fresh, upgrade and rerun cases on the production Postgres major version (checked-in Compose is 16 while CI uses 17). A database rollback cannot undo chain effects.

**Liveness atomicity:** issue bounded TTL rows keyed by session/wallet/build with nonce/challenge. Completion locks that row, verifies expiry/attestation/request binding, records the accepted result and updates actor verification in one transaction. Same-request retry returns the stored result; different digest/attestation is a conflict. Today the in-memory session is consumed before DB commit/rate check, so a failed commit can strand a valid attempt. Persist only the minimum evidence; delete expired material under the retention policy, retain necessary replay identifiers for their validity horizon. Restart/replica switching must not create a second acceptance.

**Lock discipline:** define one documented order and use conditional updates/version numbers for transitions. Refactor pair→actor versus actor→judgment/prepared inversions; retry genuine serialization/deadlock errors with bounded jitter. A stale worker result must not overwrite a newer epoch. New task leases limit outstanding assignments; assignment expiry never erases an accepted judgment or on-chain liability. Expiry cancellation/release is a durable job with tombstones.

### 3.5 Durable async queue and financial state machine

Use **Postgres transactional outbox/job table for v1**, one per product, rather than an in-process task or Redis-only financial queue. This removes the DB/queue dual-write gap and avoids adding a broker before throughput requires it. Redis is disposable for caching, not the money ledger. A broker may later dispatch job IDs while Postgres remains authoritative.

Job fields: immutable logical ID/type/entity, payload schema version/hash, priority, status, attempt count, `next_attempt_at`, lease owner/expiry, fencing version, redacted last error, creation/update times. Unique `(job_type, entity_id, operation_version)` prevents duplicate obligations. Workers claim small batches with `FOR UPDATE SKIP LOCKED`, commit leases immediately, then perform RPC outside locks. Lease heartbeats and compare-and-set completion guard stale workers; on-chain receipts remain the final protection against duplicate external effects.

Proposed flow:

1. Client submits stable idempotency key + assigned pair/answer. In one short transaction authenticate, enforce assignment/policy/limits, insert immutable judgment and reservation job, reserve maximum reward exposure, commit. Return `202` with judgment/operation ID and status. Same key/body returns the prior operation; same key/different body returns 409. Keep pair/wallet uniqueness as a second invariant. Add proposed `GET /judgments/{judgment_id}` and `GET /operations/{operation_id}`, wallet-scoped.
2. Worker reserves collateral using the existing judgment ID. Only a confirmed valid reservation counts toward quorum. A chain failure never counts as a vote. If late or canceled, tombstone/release logic prevents a subsequent reservation from resurrecting it.
3. A short pair-locked transaction computes consensus once, freezes reward amount/rate-policy version and each enforcement decision, then adds payout/release/enforcement jobs. Neutral choices do not count as dissent. Bounded reroutes prevent unlimited work/cost; unresolved deadline produces a documented cancellation/release outcome.
4. Payout worker validates obligation, signs an attempt, persists signed bytes/signature/expiry **before sending**, broadcasts, and checks finality. Retain all attempt signatures when a blockhash expires; do not overwrite evidence. Retry identical bytes while valid. Rebuild only after checking prior signatures and bound receipts; late arrivals cannot create a second effect.
5. Preserve current payout-before-enforcement ordering for substantive votes until the economics review explicitly approves otherwise. A temporary payout outage must not discard an enforcement decision or freeze collateral indefinitely: define a separately reviewed, journaled release/cancellation policy for prolonged outage. No operator edits a Boolean to pretend a transfer succeeded.
6. Update paid totals only from verified finalized effects; track consensus complete, payment pending, enforcement pending and batch anchoring separately. Enqueue anchor after the approved finalization boundary. `post_batch` currently retries `init` even if a previous anchor landed; inspect existing Batch owner/discriminator/root and matching transaction to recover success, or quarantine mismatches.
7. Autonomous reconciler periodically scans unreserved judgments, pending payouts/enforcement, unanchored finalized batches, expired leases and unresolved prepared transactions. No returning user is required. Priority favors release/recovery of existing liabilities over new work.

Retry transient transport/429/node-behind errors with exponential backoff/jitter and per-provider budgets; isolate deterministic authorization/mint/layout/receipt errors for investigation. A dead-letter job remains an unpaid or unresolved ledger liability and pages an operator. Retry count never deletes financial obligations. Admin replay is audited, role-restricted and reuses the same logical ID. Provide a per-build pause switch for new admissions and an independently controlled payout signer pause.

Do not occupy a worker execution slot for the whole finality interval: persist `broadcast/pending_confirmation`, release the lease, and schedule a batched confirmation pass. The initial concurrency limit bounds active network/signing calls, while outstanding transactions have a separate cap. Benchmark both limits and shared fee-payer/vault contention; if measured settlement capacity is below the proposed burst envelope, reduce admission before launch.

**Compatibility:** introduce an explicit API version/capability contract; old clients must not mistake accepted work for finalized payment. The Android pending balance already derives earned minus settled, but needs asynchronous operation states and refresh behavior. Stage new clients/backend in devnet before requiring the version at public launch. Preserve USDC field names and independent version history; wrong-family clients fail visibly rather than defaulting missing JSON amounts to zero.

### 3.6 Caching, admission controls and DDoS posture

**Caching:** separate product Redis credentials/instances and network/build namespaces. Cache approved immutable task metadata by content/version hash; wallet stats for 5–15 seconds with a freshness timestamp; network/config checks briefly with periodic refresh; blockhashes only within verified validity. Invalidate stats after committed ledger transitions. Never use a cached bond balance, risk decision or treasury total as authorization to spend; atomic program/DB checks remain authoritative. Do not cache bearer-authenticated responses in a shared CDN. Do not put signed media URLs or private rubrics in generic telemetry/cache dumps. Redis loss may degrade display performance, but must not lose accepted work or liveness proofs.

**Two layers of limiting:** edge/IP protections before DB work, plus Redis atomic token buckets for authenticated wallet/device/cohort/endpoint and product-global budgets. Persist monetary budgets in Postgres. Trust forwarded IPs only from configured edge/Caddy peers; ignore arbitrary client headers. Do not rely on IP identity alone behind mobile carrier NAT. Invalid requests must consume abuse quotas independently of rolled-back business transactions; current DB counters can roll back with request failure.

Starting limits to load-test, not immutable product policy:

| Surface | Initial policy per product | Failure behavior |
|---|---|---|
| Auth challenge/verify | Retain wallet challenge 10/min; edge IP challenge/verification budget around 30/min with NAT testing and global CPU ceiling; cap challenge rows/TTL. | 429 with `Retry-After`; invalid signatures consume verification budget. |
| Liveness | 10 sessions/hour/wallet initially; separate completion-attempt bucket; bounded active sessions/device/cohort. | Reject excess before expensive attestation or state consumption; same accepted request is replay-safe. |
| Read/status | 60/min/wallet aggregate with burst 20; cache/coalesce refreshes; global 100 RPS starting envelope. | 429 rather than pool exhaustion; client backs off. |
| Judgment | 12 new submissions/min/wallet, burst 3; initially one active assignment/wallet; product ceiling 10 accepted/s only while worker/treasury capacity supports it. | No side effect on refusal; existing-operation status/retry remains available under a separate budget. |
| Bond prepare/confirm/reconcile | 5 new preparations/min/wallet; dedupe confirm jobs; at most one expensive scan/operation and a small scan budget per wallet. | Enqueue or return current pending operation; no repeated 2,000-signature walks from HTTP. |
| Faucet, devnet only | Existing max 5 mints/wallet plus independently reserved daily global token/SOL budget, wallet/IP/device quotas and a durable idempotent attempt. | Mainnet route absent/disabled. Devnet global check cannot race across fresh wallets. |
| Export/admin | Ordinary wallet denied; role-specific concurrency, row/byte/job ceilings. | 403 or bounded asynchronous export; audit every request. |

Use a conservative fallback if Redis fails: existing read/status requests can use bounded local protection; new high-cost or paid work fails closed with retryable maintenance status. Do not silently permit unlimited traffic. Per-product global ceilings and a shared host emergency ceiling protect USDC when SKR is attacked and vice versa.

**Edge/host:** scope a managed edge proxy/WAF with verified API and future video bandwidth support; choose plan after cost/limits review rather than assuming free proxying covers media. Add upstream volumetric protection, request/body/header/time limits, TLS, bot controls compatible with native clients, and credential-stuffing/signature-abuse rules. Do not put browser-only challenges on native API paths. Configure origin firewall/tunnel or authenticated edge-to-origin transport so direct-origin requests cannot bypass limits; rotating an IP without blocking old/direct access is insufficient. Keep Caddy/backend/Postgres/Redis/admin ports private, SSH restricted, and separate emergency operator access. The shared Caddy deployment may serve other workloads: inventory blast radius before rule changes. Edge DDoS tests should use a controlled staging harness, never unsolicited load against public providers.

### 3.7 RPC provider and signer strategy

The current public devnet endpoint is suitable for development, not a production service guarantee. Public rate limits are mutable; private access is required for production according to [Solana's cluster guidance](https://solana.com/docs/references/clusters). Provider choice must match peak method mix, historical lookups, subscriptions, geographic latency and support, not just advertised requests/second; use [Solana's provider selection criteria](https://solana.com/docs/rpc/providers).

* **Environment separation:** keep localnet for destructive/chaos tests and devnet for integration; provision paid primary + independent fallback mainnet RPCs with separate credentials and per-product quotas. Devnet fallback stays devnet. Mainnet must never fail over to another cluster. Persist the verified genesis/program/mint tuple with each deployment and obligation domain.
* **`rpc.py` / `config.py`:** reusable HTTP client with bounded connections and connect/read/overall deadlines; support named endpoints, quotas, circuit breakers, error categories and per-method latency. Pass remaining deadline into every inner history call. Honor `Retry-After`, use backoff/jitter, prevent retries at client/API/worker layers from multiplying.
* **Read failover:** check genesis and slot health; use consistent commitment and minimum context where supported. A stale provider returning no receipt is not proof that a transaction did not happen. Cross-check uncertain finalized effects using persisted signatures and the second provider; retain unresolved state if providers disagree.
* **Write failover:** send the same signed transaction bytes/signature to the fallback when appropriate. Do not generate another payment ID or different amount to recover from a timeout. After expiry, reconcile all attempts/receipt before signing replacement. Add simulation and bounded priority/compute budgets; enforce maximum SOL fee spend in signer policy.
* **Confirmation:** batch `getSignatureStatuses`; optionally use WebSocket subscriptions with polling fallback. Preserve finalized checks for accounting; expose submitted/confirmed/finalized as distinct user states. Prefer known signatures to account-history scans; background scans need durable cursor/deadline and archive-history coverage.
* **Quota arithmetic:** benchmark RPC requests per accepted vote, confirmation polls and occasional full transaction reads. Allocate method-specific read/write/scan pools with at least measured burst headroom. Provider throttling triggers worker backpressure and ultimately admission pause; it must not exhaust API threads or DB connections.
* **Signer boundaries:** API carries no verifier or treasury secrets. Signer checks product/network/program/instruction allowlists, obligation ID/hash, destination, amount, fee cap and treasury lane before signing. Backend verifier currently doubles as slash authority; split authority roles in the token/program review. A managed signer is useful only if it supports the actual Solana transaction/Ed25519 flow and recovery requirements; prove compatibility before selecting it.

Acceptance includes primary RPC 429, malformed responses, high latency, stale nodes, unavailable archive history, unknown broadcast outcome, blockhash expiry and complete provider outage. Finalized accounting must remain correct through failover. Reserve SOL separately for fee payer, ATA creation, payment/liability rent, anchors and priority fees; a token-funded treasury with no SOL is not operational.

### 3.9 Backup, recovery and release operations

* Per-product encrypted off-host base backups plus continuous WAL archiving/PITR; initial objective **RPO ≤5 minutes, RTO ≤60 minutes** for ordinary DB/host loss. Keep 30 days PITR and longer financial snapshots according to the approved retention policy; test cost and restore time at projected DB size. A local Docker volume or dump on the same VPS is not DR.
* Separate backup credentials and deletion protection from runtime credentials; include deployment manifests, migration checksums, release artifacts, ledger/attempt history and approved media manifests. Keys use a separately controlled recovery process, not plaintext database backup attachments. Keep neutral names in storage catalogues and notifications.
* Recovery drill: stop admissions/signing, restore product DB in isolation, validate family/network identity, restore schema-compatible code, reconcile post-backup finalized receipts/liabilities/anchors and all known attempts, rebuild disposable caches, compare ledger/chain totals, then reopen gradually. Never restore an old DB and resume payouts without reconciling chain effects. Retained signed attempts and chain receipt discovery must cover writes after the backup; loss of that evidence extends RTO and requires quarantine.
* Monthly restore rehearsal and quarterly host/provider-loss exercise. Include independent USDC recovery while SKR continues, and the reverse. Protect backups from cross-product role access.
* Deploy with immutable manifests, schema expansion first, canary API/worker rollout, drain in-flight requests and stop leasing new jobs on shutdown. Roll back application images only while schema/wire compatible. Financial state and chain writes are never “rolled back” by reverting Git. Retain a forward-repair path for program/account changes.

At 100,000 pair views/day that is about 500 GB/day of delivery, multiplied by replays and reduced only at the origin by cache hits. Price CDN egress/request charges and transcoding with a hard per-product budget; caching does not eliminate viewer egress. Benchmark selected providers rather than committing to a pricing assumption.

**Risks:** contextual disclosure despite neutral labels, redistribution, CDN authorization mistakes, media-parser vulnerabilities, playback bias, excessive bandwidth, app memory/thermal failures. **Acceptance:** reviewed clean sample library; no unapproved asset reachable by identifier; signed URL expiry/revocation and cross-wallet/build denial work through cache hits; Seek/Range and resume work on weak/mobile networks; target first frame p95 <2 seconds on the agreed test network with rebuffer ratio <2%; no player leaks after repeated navigation; A/B mapping and payout correctness unchanged; ingest retry produces one immutable approved asset/pair; privacy/store descriptions updated if data practices change.

### 6.2 Treasury sizing and exposure limits

Obtain a funded operating budget before admitting paid work. Let `A` = payable aligned judgments/day, `r` = base token reward, `m` = average multiplier, `N` = payable neutral answers/day, `f` = flat reward, `D` = reserve days, `b` = contingency fraction, and `L` = existing unpaid plus maximum reserved exposure. Required token inventory:

`T_required = L + D × (A × r × m + N × f) × (1 + b)`.

Illustrative **test-rate scenario, not proposed mainnet pricing**: current defaults `r=0.02`, `f=0.005`, 10,000 aligned answers/day, average multiplier 1.25 and 1,000 paid neutral answers/day yield 255 tokens/day; 30 days plus 30% buffer is 9,945 tokens **plus L**. Stress the maximum multiplier 2×, eligible judge count, bounded reroutes, wallet farms and accepted-but-unresolved assignments rather than funding only the average. The required cash acquisition budget depends on actual $SKR price/liquidity and approved procurement; no price assumption is made here.

Track SOL separately: transaction count × capped fee/priority allowance + ATA creation + payment/liability account rent + anchors + operational reserve. Permanent per-vote receipt/liability accounts accumulate rent and ledger size; measure costs from the proposed compiled layouts and current rent/fees before launch. Any later receipt pruning must retain replay protection and merits a separate design.

Reserve maximum reward liability in the DB when accepting work, settle actual amount once, and release unused budget exactly once. Available admission budget = verified vault funds minus outstanding/reserved obligations and safety buffer. Serialize budget updates; do not let multiple API replicas spend the same balance snapshot. Monitor cold/hot reserves separately; hot vault contains a deliberately bounded few days of approved exposure, with refill alerts and signer caps. Exhaustion pauses **new paid work** while preserving previously earned debts and status visibility. User bond collateral and penalty vault funds are not operating income or spendable payout treasury by default.

### 6.3 Bond/slash economics and participant protection

Current defaults in [config.py](/home/hermes/capture-clock-in/backend/seeker/config.py) and [judge_leveling.py](/home/hermes/capture-clock-in/backend/seeker/judge_leveling.py): minimum bond 1 token at six test decimals, base reward 0.02, neutral reward 0.005, up to 2× multiplier, window 100, penalty below 45% agreement after 20 judged items; first warning freezes withdrawal and another penalty can slash the full vault. Program cooldown is 24 hours, and pending liabilities independently block withdrawal. These are demo parameters, not validated mainnet economics. A small sample can currently reach a high multiplier because leveling uses agreement alone.

Model expected honest earnings/loss, correlated disagreement, adversarial majority, neutral farming, wallet-reset cost, max concurrent exposure and time to release collateral. Maximum outstanding work must relate to bond size; a pending counter alone does not allocate collateral per task. Add confidence/minimum-sample safeguards, independently checked quality evidence and an appeal/hold/reversal design **before** real slashes. Once a slash is finalized, a backend flag cannot reverse it; any compensation requires a funded, audited separate transfer. Review the indefinite first-warning freeze and introduce a bounded resolution/appeal path. Never slash for infrastructure/playback failure or neutral responses.

Publish clear bond amount, cooldown, pending-liability lock, earning conditions, maximum loss, dispute procedure and custody/authority facts using neutral product language. Policy approval and economic sign-off gate final program parameters and store claims. A limited real-value pilot can keep automated slashing disabled only if this is an explicit, accurately disclosed mode with program enforcement and an agreed alternative abuse budget; it is not a silent override.

**Risks:** signer theft, wrong mint/decimal/token program, reusable receipt identities, treasury shortfall, fee/rent escalation, harmful consensus penalties, upgrade misconfiguration, store policy changes. **Acceptance:** independent program review and remediation; SBF tests for transfer conservation (treasury decreases exactly as recipient increases, mint supply unchanged), duplicate/conflicting ID rejection, wrong vault/mint/authority, caps/pause, empty treasury/fee payer, expiry/failover, liability-safe withdrawal and boundary economics; signed configuration/custody/treasury plan; completed devnet canary and a separately authorized bounded mainnet validation before public claims. Zero mint fallback on mainnet.
